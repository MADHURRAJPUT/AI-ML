# 6.5 Build #2 — A Kaggle tabular competition, end to end

> Curriculum build: *"A Kaggle tabular competition end to end with a
> gradient-boosted model and a proper validation scheme."*

This folder is a working, minimal project skeleton. Your job this week is to
**make it yours**: run it, understand every line, improve it with experiments
you log, and publish it as your first portfolio repo.

## The competition: Spaceship Titanic

[kaggle.com/competitions/spaceship-titanic](https://www.kaggle.com/competitions/spaceship-titanic)
— a permanent "getting started" competition: ~8 700 passengers, predict
`Transported` (binary), metric **accuracy**. Small enough to iterate in seconds,
messy enough to need real feature engineering, and it has a **group structure**
(`PassengerId = gggg_pp` — people travelling together) that punishes naive CV.

> Prefer something else? Any binary tabular competition works: `train.py --dataset csv --csv path --target y --id-col id`.
> Good alternatives: a current *Playground Series* episode, or *Home Credit* if you want a big, realistic one.

### Get the data

```bash
pip install kaggle                     # put your API token in ~/.kaggle/kaggle.json
kaggle competitions download -c spaceship-titanic -p data/spaceship
unzip data/spaceship/spaceship-titanic.zip -d data/spaceship
```

(`data/` and `reports/` are git-ignored — never commit competition data.)

### Run it

```bash
python train.py                                              # offline demo on the churn data
python train.py --dataset spaceship --data-dir data/spaceship
```

Output: a results table in the terminal, `reports/<dataset>/results.md`,
`params.json`, and for Spaceship a `submission.csv` ready to upload.

## What's in the skeleton (read it in this order)

| File | What it does | Lesson it applies |
|---|---|---|
| `data.py` | loaders returning a `DatasetSpec` (target, id, **group column**, metric) | 6.1 |
| `features.py` | stateless row-wise features; separate preprocessors for linear models (impute + indicators + scale + one-hot) and trees (passthrough + ordinal) | 6.3 |
| `train.py` | `StratifiedGroupKFold` when groups exist; baseline → logistic regression → LightGBM; **early stopping on a slice of each training fold** (never the validation fold); OOF metrics; threshold chosen on OOF; permutation importance on a held-out fold; fold-averaged test predictions | 6.1, 6.2, 6.4, 5.3 |

### Reference output on the offline churn data

| model | ROC-AUC (5-fold) | OOF PR-AUC | OOF log loss |
|---|---|---|---|
| baseline (prior) | 0.5000 ± 0.0000 | 0.326 | 0.631 |
| logistic regression | 0.7856 ± 0.0115 | 0.619 | 0.513 |
| LightGBM | 0.7734 ± 0.0102 | 0.597 | 0.524 |

(Logistic regression wins on churn because that synthetic data was generated by
a logistic model. On Spaceship Titanic, expect LightGBM to win.)

## Your tasks this week (≈7 h)

**Day 1 — baseline & EDA (1.5 h)**
1. Download the data, run `train.py --dataset spaceship`, submit `submission.csv`. Record CV accuracy vs public leaderboard accuracy in `experiments.md`.
2. Do the week 3 EDA checklist on `train.csv`. Note: missingness per column, how `CryoSleep` relates to spending, how `Transported` varies by `Deck`/`Side`/`HomePlanet`.

**Day 2–3 — experiments (4 h).** One change at a time; log CV mean ± std each time. Ideas, roughly in order of value:
- `CryoSleep` passengers can't spend: impute their missing spend as 0, and missing `CryoSleep` as True when spend is 0.
- Group-level features: fill missing `HomePlanet`/`Deck`/`Side` from other members of the same group (no labels involved → no leak).
- Last-name family size from `Name` (careful: compute on train+test without labels).
- Cabin number bins (`CabinNum // 300`) — the ship's layout matters.
- LightGBM tuning: `num_leaves` ∈ {7, 15, 31}, `min_child_samples` ∈ {20, 50, 100}, `learning_rate` 0.01–0.05.
- Try CatBoost with native categoricals; average its OOF probabilities with LightGBM's (blend weight chosen on OOF).
- Check: does `StratifiedGroupKFold` vs plain `StratifiedKFold` change your CV? Which one tracks the leaderboard better?

**Day 4 — ship (1.5 h)**
- Final submission; compare CV vs leaderboard; explain any gap.
- Write the README (template below), push to a public repo, write the short post.

### Rules for yourself
- **Never tune on the leaderboard.** Choose by CV; submit to confirm. If a change improves the LB but not CV, it's noise.
- **Fixed folds and seed** for every experiment, so differences are comparable.
- A change counts only if it beats the previous best by more than the fold std (or holds across 2–3 seeds).
