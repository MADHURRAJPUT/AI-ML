# 9.6 Build: the training-debugging log

> Curriculum build: *"A training-debugging log: deliberately break things (bad
> LR, no normalisation) and record what the loss curve does."*
>
> Phase checkpoint: *"given a loss curve that plateaus or explodes, you can name
> three likely causes and the fix for each."*

Most training bugs don't crash — they produce a plausible-looking but wrong
loss curve. The fastest way to recognise them is to have *caused* each one
yourself and seen its signature. `break_training.py` runs 15 experiments on
the same model and data, auto-labels each curve, and writes a log.

```bash
python break_training.py      # ~35 s -> outputs/debugging_log.md and outputs/loss_curves.png
```

Open `outputs/loss_curves.png` next to the table below and study each panel.

### Things worth noticing

- **Three different bugs, one curve.** Dead ReLUs, a deep sigmoid net and shuffled labels all sit flat at **ln 10 = 2.30**. The curve tells you *nothing is being learned*; it can't tell you why — that needs the checks below.
- **Starting loss is a free diagnostic.** For K classes it should be ≈ ln K. 9.3 (raw pixels), 65 (std-1 init) or 110 (LR 0.1 after a few steps) all flag a scale problem before training has even begun.
- **Some bugs hide behind decent accuracy.** Softmax-twice still reaches 84 % accuracy, but its loss can't go below ln(1 + 9/e) ≈ 1.46 — and its probabilities are useless.
- **Adam masks problems.** Raw 0–255 inputs still train under Adam (per-parameter step sizes adapt) — with SGD + momentum the same bug sends the loss to ~10¹⁵ and it never recovers. Don't rely on the optimiser to hide a preprocessing bug.
- **Forgetting `zero_grad()`** looks like learning for a few dozen steps, then degrades — a curve that goes *down then up* in training loss (not validation) is a red flag.

## The playbook (memorise this — it's the checkpoint)

### Loss explodes / NaN

| Likely cause | How to confirm | Fix |
|---|---|---|
| Learning rate too high | LR range test; loss spikes right after warmup ends | lower LR (÷3–10), add/lengthen warmup |
| Numerical bug: log(0), division by ~0, exp overflow | `torch.autograd.set_detect_anomaly(True)`; check custom code | use log-softmax/`*WithLogits` losses, add eps, clamp |
| Exploding gradients (deep/recurrent nets, bad init) | log grad norm per step; spikes before the NaN | gradient clipping (1.0), proper init, normalisation, residuals |
| A bad batch (corrupt input, huge values) | log the batch index; inspect it | data validation, clipping |
| fp16 overflow | only happens with fp16 autocast | bf16, or `GradScaler` (9.5) |

### Loss plateaus

| Likely cause | How to confirm | Fix |
|---|---|---|
| **Stuck at ln K from step 0:** no gradient reaches the weights (dead ReLUs, saturated sigmoid/tanh, vanishing gradients) | activation stats (% dead / saturated), grad norm per layer (9.1) | He init, ReLU/GELU, normalisation, residual connections |
| **Stuck at ln K:** data/label bug (shuffled, misaligned, wrong column) | **overfit one batch** — if even that fails, it's the pipeline; look at (x, y) pairs | fix the pipeline |
| LR too low | update/weight ratio ≪ 1e-3 | raise LR |
| Loss floor above 0 with OK accuracy | the minimum achievable loss is > 0 | remove the extra softmax/sigmoid; losses take logits |
| Model too small / features insufficient (high bias) | train loss itself high; bigger model helps | more capacity, better features, train longer |
| LR schedule decayed too early | LR in the log is ~0 | longer schedule, higher floor |

### Train goes down, validation goes up

Over-fitting (9.3) — or leakage/shift between splits (week 6). More data,
augmentation, dropout/weight decay, smaller model, early stopping; and check
the splits really come from the same distribution.

### The four checks before any long run (week 7.3)

1. Gradient-check custom backward code.
2. Initial loss ≈ ln K (or the base-rate entropy).
3. Overfit a single batch to ~0.
4. Look at a few input/label pairs with your own eyes.

3. Add a "label off-by-one" experiment (`y = (y + 1) % 10`). What does the curve look like, and why is it *not* stuck at ln 10?

<details><summary>Answers</summary>

1. Inputs to the second softmax are probabilities in [0, 1]. The best case puts 1 on the true class and 0 elsewhere: p = e/(e + 9) ≈ 0.232 → loss = ln(1 + 9/e) ≈ 1.46.
2. Typically the loss's log-softmax after logits overflow to inf (inf − inf = NaN) — run it to see the exact trace.
3. It trains normally — the mapping is still learnable (it's just a relabelling); validation accuracy against the *true* labels is ~0. A healthy-looking curve with absurd validation metrics means the train and eval label pipelines disagree.
